========================
PROJECT OVERVIEW
========================
Project name: Trekking Management Application V2 (TMA)
Course: Modern Application Development II (MAD-II)
Type: Full-stack web app for managing treks with 3 roles:
1) Admin
2) Trek Staff
3) User / Trekker

Problem it solves:
Adventure groups often manage treks with spreadsheets/calls. This app manages trek creation, staff assignment, slot booking, participant tracking, history, Redis caching, and Celery background jobs in one system.

========================
MANDATORY TECH STACK (USED)
========================
- Flask: REST API backend
- Vue.js (CDN, Vue 2): frontend UI
- Jinja2: only entry HTML page (templates/index.html), NOT full UI
- Bootstrap 5: styling only CSS framework
- SQLite: database
- SQLAlchemy via Flask-SQLAlchemy: models + db.create_all()
- Redis: caching + Celery broker
- Celery (+ Beat schedule configured): batch jobs
- JWT (PyJWT): authentication tokens
- Werkzeug: password hashing

NOT used (optional course extras skipped):
- Vue CLI
- Chart.js
- PWA
- PDF reports (HTML report used instead)
- Payment simulation

Important UI fix:
Vue and Jinja both use {{ }}. templates/index.html wraps Vue markup in {% raw %} ... {% endraw %} so Jinja does not parse Vue bindings.

========================
FOLDER / MAIN FILES
========================
Repo (example): mad2-trekking-management

- app.py : Flask app factory, all API routes, serves UI
- models.py : User, StaffProfile, Trek, Booking
- seed.py : creates default Admin after DB creation
- auth.py : JWT create/decode, login_required, role_required
- config.py : DB URI, JWT secret, Redis URL, SMTP/webhook env vars
- cache_util.py : Redis get/set/delete with TTL
- celery_worker.py : Celery app + beat schedule
- tasks.py : daily reminders, monthly HTML report, CSV export
- templates/index.html : Jinja shell + Vue UI
- static/app.js : Vue methods calling APIs
- requirements.txt
- README.md
- PROJECT_REPORT.md / PROJECT_REPORT.pdf
- exports/ : generated CSV/reminders/report files (gitignored mostly)
- tma.db : SQLite DB created automatically (not manually in DB Browser)

========================
DATABASE MODELS
========================
Unified User model with role field:
- role = "admin" | "staff" | "user"

1) users
- id, name, email, password_hash, role, phone
- is_active, is_blacklisted, created_at

2) staff_profiles
- id, user_id (FK users), contact_details, status

3) treks
- id, name, location, difficulty (Easy/Moderate/Hard)
- duration (days), available_slots
- assigned_staff_id (FK users)
- status: Pending / Approved / Open / Closed / Completed
- start_date, end_date, description

4) bookings
- id, user_id, trek_id
- booking_date
- status: Booked / Cancelled / Completed
- payment_status (optional, default Pending)

Relationships:
- User 1—0..1 StaffProfile
- User(staff) 1—many Trek via assigned_staff_id
- User(trekker) 1—many Booking
- Trek 1—many Booking

Admin seeding:
- seed.py creates Admin if missing:
  email: admin@tma.local
  password: admin123
- No Admin registration in UI.

========================
AUTHENTICATION & RBAC
========================
- Login for all roles via POST /api/login → returns JWT + user
- Register only for Trekkers via POST /api/register (role always forced to "user")
- Staff: no self-registration; Admin creates staff
- Admin: predefined only
- Frontend stores token/user in localStorage
- API protected with Authorization: Bearer <token>
- role_required("admin"|"staff"|"user") enforces access
- inactive/blacklisted users cannot login / authorized APIs reject them
- After login, Vue shows role-specific dashboard

========================
CORE BUSINESS RULES (IMPORTANT FOR VIVA)
========================
1) Booking allowed only if trek.status == "Open"
2) Prevent overbooking: available_slots must be > 0; slot decremented on book
3) Prevent duplicate booking for same user+trek (non-cancelled)
4) Cancel sets booking Cancelled and increments slots back
5) Only assigned staff can update that trek / see participants
6) Users see only their own bookings
7) Admin can see all bookings
8) Blacklisted/inactive users/staff blocked
9) DB created programmatically via models + db.create_all()

========================
REDIS CACHING
========================
- cache_util.py uses Redis URL redis://localhost:6379/0
- Caches:
  - open_treks
  - all_treks
- TTL from config (CACHE_TTL_SECONDS, e.g. 60)
- cache cleared on trek/booking changes via clear_trek_cache()
- if Redis down, cache functions fail softly (app can still run, jobs may fail)

========================
CELERY JOBS
========================
Broker/backend: Redis

1) Daily reminders (tasks.send_daily_reminders)
- finds booked treks starting within ~3 days
- writes exports/daily_reminders.txt
- also tries webhook and/or SMTP if env vars set

2) Monthly report (tasks.send_monthly_report)
- HTML report with completed treks, participants, popular treks
- saves exports/monthly_report.html
- also tries webhook/email if configured

3) CSV export (tasks.export_user_history)
- triggered by user from UI: POST /api/export/history
- async Celery task
- CSV columns: User ID, Trek Name, Location, Booking Status, Dates
- UI polls /api/export/status/<task_id> and shows alert when done
- file: exports/user_<id>_history.csv

Celery Beat schedule exists in celery_worker.py for daily/monthly intervals.
For demo, tasks can be called manually:
celery -A celery_worker.celery call tasks.send_daily_reminders
celery -A celery_worker.celery call tasks.send_monthly_report

Notification env vars (optional):
TMA_WEBHOOK_URL, TMA_SMTP_HOST, TMA_SMTP_PORT, TMA_SMTP_USER,
TMA_SMTP_PASSWORD, TMA_SMTP_FROM, TMA_REPORT_TO
